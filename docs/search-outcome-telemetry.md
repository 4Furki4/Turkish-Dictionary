# Submitted search outcomes

Stage 3 of the dashboard roadmap. Collection is separate from `search_logs` (resolved entry visits, including direct visits) and `word_query_latencies` (successful submission-to-visible-result duration). These datasets have different populations and must not be combined into a failure-rate denominator.

## Attempt contract

- An explicit submission in `SearchContainer` (including selected suggestions and the mobile search dialog) or the desktop navbar creates one random UUID. Merely typing, autocomplete, prefetching, page visits, reloads and background revalidation do not create attempts.
- The tab stores one pending marker, valid for at most two minutes. It survives document navigation; a departing card cannot finish a full navigation. Known older, superseded destinations cannot finish or cancel the newer marker.
- A displayed result produces `resolved`; a completed lookup with no match produces `no_result`; a failed lookup, unavailable offline dataset or local read error produces `error`. Rate limiting is an error, never evidence of a missing word. `resultCount` is the number of displayed word cards (pattern searches are currently capped by the offline lookup), not an exhaustive database count.
- A new submission terminates the older pending attempt as `superseded`. Leaving its search route or using browser history terminates it as `cancelled`. Those outcomes have zero results and are excluded from completed-search denominators.
- Consuming the marker precedes delivery, so repeated renders, Strict Mode, refreshes and cloned-tab duplicate delivery cannot count the same ID twice within the retention horizon. A stalled/expired marker is discarded; closing a tab or losing a document before its outcome may leave no report. No terminal result is fabricated for an unobserved completion.
- `source` is the result's online or installed-dataset lookup path, including an online attempt that failed. Cached online cards remain `online`; local/cache-installed cards and patterns are `offline`. It is not an assertion about whether a network request occurred. `entryPoint` distinguishes `search` and `navbar`; the server derives `kind=word|pattern` from underscores. Locale is `tr|en`.
- The browser sends outcomes only when `navigator.onLine` is true. Offline completions consume the marker without queuing or replaying after reconnection. A bounded, memory-only startup buffer covers result effects that run before the reporting layout effect. There are no network retries or persistent outcome queue.

## Text and access policy

Only NFC-normalized, trimmed, Turkish-lowercased dictionary terms are sent. Repeated Unicode spaces collapse to one space; curly apostrophes normalize to straight apostrophes. The strict ingestion schema accepts at most 100 UTF-16 code units of letters, combining marks, spaces, apostrophes, hyphens and pattern underscores, with at least one letter. It rejects digits, obvious email/phone/URL forms, markup, line breaks, controls and invisible format characters rather than redacting them into misleading terms. This deliberately excludes some legitimate alphanumeric and punctuated searches. A spelling or a personal name consisting solely of letters cannot reliably be distinguished from a dictionary term; this filter does not promise to identify all personal information.

The event stores only UUID, normalized query, locale, entry point, source, derived kind, terminal outcome, bounded result count and server receipt time. It accepts no user/account ID, IP, user-agent, email, full URL, client timestamp, freeform error or duration. The original text is never added to the duration-only latency endpoint. Context network/account identifiers are used only by the existing independent telemetry limiter and are not analytics dimensions. No outcome-read API is exposed in this stage; later administrative views must use `adminProcedure`.

Known search-engine user agents are ignored by outcome ingestion. Every report uses its own 30-per-minute outcome bucket, separate from both dictionary browsing and the existing 30-per-minute latency bucket; crawler identification does not create an exemption. A resolved attempt emitting both reports therefore cannot halve either budget or give no-result attempts a larger collection allowance. User-agent spoofing, scripted submissions, blocked JavaScript, dropped reports, disconnected operation, excluded text and collection outages all limit coverage. These are browser-reported attempts, not verified human traffic. Future no-result rates must use `resolved + no_result` from the same source, kind, locale and receipt window; errors and cancellations need separate labels.

## Storage, deduplication and retention

`search_outcomes` retains the query-bearing events. Its UUID primary key deduplicates delivery. `search_outcome_daily_totals` has one UTC receipt-day bucket for each locale/entry point/source/kind/outcome and a count; it contains no term or event/visitor identifier. Event insertion and the daily increment share a transaction. A duplicate inserts neither another event nor another count; an aggregate-write failure rolls back the raw event. Ingestion has two-second statement and one-second lock limits and runs independently of dictionary navigation/results.

The authenticated existing `/api/update-view-counts` daily cron now prunes events older than 90 elapsed days **before** view aggregation, including runs with no view logs. It retains events exactly at the cutoff until the next pass. A successful daily cadence therefore gives a maximum retention of approximately 91 days; cron failures extend it and must be resolved through the existing monitor. Daily totals remain after raw event deletion. The cron response includes its deleted count; a retention failure fails the job visibly. Query-level gap analysis is limited to the retained event window, while older totals cannot reconstruct query text. Duplicate IDs can be accepted again after their raw row expires; there is no indefinite identifier tombstone.

Stage 4 adds query-bearing current triage decisions in `search_gap_reviews`. The same job removes decisions whose update is older than the cutoff and reports `reviewsDeleted`; decisions already become inactive at read time after 90 days. Apply migration `0053_search_gap_reviews` before deploying the updated job. See [the search-gap contract](dashboard-search-gaps.md) for the stored fields, purpose, access and deletion behavior.

## Rollout and validation

Generate `0052_search_outcomes` from `db/schema/search_outcomes.ts` and apply it before deploying the new ingestion/cron code. Follow the database runbook for environment migrations, including ledger verification and the production backup requirement. The existing scheduled view-count job supplies retention; confirm its authenticated run and monitor after deployment. This change does not install or modify an environment's cron schedule.

Local validation uses only the fixed disposable CI database. Its legacy migration history does not bootstrap a fresh schema; the new generated SQL is applied directly to the already prepared CI schema in a transaction, then constraints, atomic deduplication, raw-event expiry and retained totals are checked. No Pi or production migration is part of this implementation.
